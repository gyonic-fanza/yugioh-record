# OCG RECORD

遊戯王OCGの戦績を、スマートフォンで記録する静的Webアプリです。GitHub Pagesでそのまま動きます。アカウントなしでも端末内で利用でき、用意されたSupabaseプロジェクトへ任意でログイン・同期できます。

## 機能（Phase 1〜3）

- 使用デッキ・相手デッキの候補付き入力。未登録の使用デッキは対戦保存時にレシピなしで登録し、レシピがあるデッキのみバージョンを選択
- デッキ登録、MAIN / EXTRA / SIDEのカード名と枚数、独立したレシピ版の追加・複製
- イベント登録とイベントごとの対戦一覧
- MATCH（最大3ゲーム）/ SINGLE記録。ゲーム別先後・勝敗、マッチ自動判定と手動修正、メモ・タグ、履歴の編集・削除
- HOMEの月間集計、ANALYSISの期間・デッキ・対面・ゲーム先後別の基本集計
- LIGHT / DARK / SYSTEM、全データのJSONエクスポート、上書き・マージ復元
- 任意のSupabaseプロジェクトとメールリンク／6桁コード認証でログインし、端末間で戦績・デッキ・レシピ・大会・タグを同期
- ANALYSISの詳細表示：デッキ・対面ごとのMATCH / GAME / 先攻GAME / 後攻GAME、デッキバージョン比較、タグ別の勝敗
- 月別MATCH内訳グラフ（対戦数と勝敗構成）、母数5 MATCH未満の注意表示
- 改訂日から用意したレギュレーションと独自期間の登録・削除・絞り込み、店舗別絞り込み、表示対象の対戦CSV出力
- 遊戯王OCG公式サイト発行のデッキ記入用紙PDFから、カード名と枚数をMAIN / EXTRA / SIDEへ取り込む機能

黒曜石と金、紫を基調にした装飾的な画面です。SVGのカード絵と紋章、縁取り、階層化した面で各画面を演出します。LIGHT / DARK / SYSTEMでも入力と数値を読みやすくしています。

## 起動方法

ローカルではこのディレクトリで `python3 -m http.server 8000` を実行し、`http://localhost:8000` を開きます。`file://` で直接開くとES Modulesがブラウザの制限で動かない場合があります。

## GitHub Pages

このディレクトリの中身をリポジトリのルートへ置き、GitHubの **Settings → Pages → Build and deployment → Deploy from a branch** で対象ブランチの `/ (root)` を指定します。サブパスでも動くよう全アセットを相対パスで参照しています。ビルドは不要です。配布版には指定済みのSupabaseプロジェクトURLと公開キーを初期設定として同梱しています。GitHub Pagesの公開操作とURL取得はリポジトリ所有者が行います。

## iPhoneのホーム画面から使用

1. GitHub Pagesへこの版を公開した後、**Safari**で公開URLを開き、共有ボタンから「ホーム画面に追加」を選びます。追加した「OCG RECORD」アイコンから起動するとアプリ画面で開きます。アプリのURLとアイコン、オフライン用の画面・スクリプトはこの版に同梱しています。GitHub Pagesのリポジトリ配下でも動作します。
2. 初回はオンラインで起動してください。以後は一度読み込んだアプリを通信のない場所でも起動でき、対戦・デッキ・イベントを端末内へ記録できます。クラウド同期・認証メール・未読み込みのPDF解析用ファイルは通信が必要です。オンライン復帰時に同期を再試行します。
3. **Safariとホーム画面版は保存領域とログイン状態が別**です。Safariでメール内リンクを開いてもホーム画面版はログインしません。下記のSupabaseメールテンプレートにコードを追加し、ホーム画面版でコードを入力してください。Safariのみに保存した戦績は、Safariで同じアカウントへ同期してからホーム画面版へログインして取得するか、SafariでJSONバックアップを出力しホーム画面版で復元します。上書き復元の前にはバックアップしてください。
4. 更新版を公開すると、通信時に画面・スクリプトを再取得します。記録本体は端末のIndexedDBに残ります。iPhoneのストレージ削除やアプリの削除に備えて定期的にJSONを保存してください。

## クラウド同期の設定（Phase 3）

1. 今回指定されたSupabaseプロジェクトを使用します。`ocg_records` テーブルが既に存在し、未ログインの読み取りが拒否されることを公開キーで確認済みです。初めて別のプロジェクトを利用する場合は、SQL Editorで [`sql/supabase.sql`](sql/supabase.sql) を実行して所有者ごとのRow Level Securityを設定します。
2. Authentication → ProvidersでEmailログインを有効にします。Authentication → URL ConfigurationのSite URL / Redirect URLsに、公開したGitHub PagesのURL（リポジトリのサブパスを含む `https://<user>.github.io/<repo>/`）を設定します。メールの送信設定や利用上限はSupabase側の設定に従います。
3. アプリには今回指定されたプロジェクトURLと **publishable key** を初期設定済みです。各端末で手入力する必要はありません。設定画面の「接続先を保存」は別プロジェクトへの接続に使い、端末ごとの手動設定がある場合はその設定を優先します。**service_role / secret keyは絶対に入力しないでください。**
4. **ホーム画面版でのログインにはSupabase側のメール設定が必要です。** Supabase Dashboard の **Authentication → Email Templates → Magic Link** を開き、メール本文に `<p>ログインコード: {{ .Token }}</p>` を追加して保存します。既存の `{{ .ConfirmationURL }}` のリンクは残して構いません。この設定をするまではメールにコードが載らないため、ホーム画面版のコード認証は使えません。
5. ホーム画面版では設定の「ログインメールを送信」でメールを送り、同じ画面の「6桁のログインコード」に届いたコードを入力します。Safariで開いた場合は従来のリンク認証も使えます。最初の同期で既存の端末データとクラウドのデータをIDごとに突き合わせます。二台目以降も同じメールアカウントでログインしてください。

ログイン後は保存・編集・削除時、オンライン復帰時、タブへ戻ったときに同期します。「今すぐ同期」でも実行できます。通信が失敗した場合は端末内データが残り、次回同期を試せます。 iPhoneでページが休止されIndexedDB接続が閉じた場合は、次の読み書き時に再接続して一度だけ処理を再試行します。削除も同期対象です。競合は各レコードの`updatedAt`を比較して新しい方を採用し、同時刻ならクラウド側を採用します。同期の途中で端末データが変更された場合は端末内の変更を保護し、次回の同期で再試行します。**端末の時計のずれや、同時刻の同一レコード編集では片方が上書きされ得ます。** 大切な変更の前後はJSONを保管してください。

初回同期後の端末データはログインしたアカウントに紐付きます。ログアウトしても端末内データは残ります。別アカウントを使う場合はJSONを保管し、「端末データと同期履歴を消去」で端末を空にしてからログインします。この操作でクラウド上のデータは消えません。「保存データをすべて削除」は、ログイン中なら次回同期時にクラウド側のデータも削除します。**クラウドへの削除反映を確認してからログアウトしてください。**

起動時に同期用ライブラリをjsDelivrから取得します。取得できなくても戦績の端末内保存は動作します。認証メールの配送設定とGitHub PagesのリダイレクトURL登録はプロジェクト側で別途必要です。Supabase標準メール配送はチームに登録された宛先以外を拒否するため、一般ユーザーへ公開する場合は独自SMTPが必要です。

## データモデル

| エンティティ | 主なフィールド | 関係 |
| --- | --- | --- |
| User（将来） | id | 初期版の全レコードの `userId` は `null` |
| Event | id, userId, name, date, venue, regulationId, deckId, rank, participants, notes | Match 1対多 |
| Match | id, userId, eventId, deckId, deckVersionId, opponentDeckName, opponentDeckId, format, playedAt, result, resultSource, notes, tags | Game 1対多。`opponentDeckId` は将来の正規化用 |
| Game | id, userId, matchId, number, turn, result | 先後・勝敗は各ゲームに属する |
| Deck | id, userId, name, regulationId | DeckVersion 1対多 |
| DeckVersion | id, userId, deckId, label, cards | 保存後は内容を変更せず、新版を作る |
| DeckCard | `DeckVersion.cards.main/extra/side` 内の `{id, cardId, name, count, type}` | `cardId` は将来カード辞書を導入した際に使用 |
| Tag | id, userId, name | Match の `tags` に文字列配列も保持 |
| Period | id, userId, label, startDate, endDate | 独自のレギュレーション。固定の初期候補はアプリ内で生成し保存しない |

各主要レコードにはUUIDと `createdAt`, `updatedAt` を保存します。Eventの日付は `date`、Matchの対戦日は `playedAt` です。以前のバックアップに時刻のフィールドが含まれていても読み込みは継続できます。MATCHとGAMEの集計母数は別々です。先後別勝率は各ゲーム単位で算出し、MATCHに先攻・後攻を割り当てません。引き分けは勝率の分母に含め、分子には含めません。両敗は敗北に含めます。相手デッキ名は自由入力です。使用デッキ名も候補付き自由入力で、未登録名は保存時にレシピなしのDeckとして自動登録します。版のあるデッキを選ぶと版の選択が有効になります。後から版を追加しても過去の「版なし」記録は変わらず、その記録の編集時にも維持できます。月別グラフはMATCHのみを表示します。

## 画面と主要フロー

HOME（概要・履歴）→ DECKS（デッキ・レシピ版とレギュレーションを登録）→ EVENTS（任意でレギュレーション・大会を登録）→ RECORD（デッキ版と相手、ゲーム別結果を記録）→ HOME / ANALYSIS（振り返り）。記録は履歴を開いて編集・削除できます。設定にはHOME右上から移動します。イベント詳細から名称・日付・店舗・レギュレーション・使用デッキ・順位・人数・メモを編集できます。既存の対戦との紐付けは維持されます。イベントの店舗は過去の登録から候補を選ぶか新しい名前を入力できます。EVENTSの店舗選択で、その店舗のイベントと対戦履歴を確認できます。ANALYSISでは集計期間とレギュレーション、店舗をそれぞれ選択して組み合わせて絞り込めます。対戦のレギュレーションはイベント設定、使用デッキ設定、対戦日の順に判定します。RECORDは直近の入力から対戦日・形式・使用デッキと版・イベント・ゲームごとの先後を引き継ぎます。使用デッキと相手デッキは同じ形式の入力・候補欄です。相手デッキは毎回選び直します。過去の相手デッキは昇順で表示され、文字を入力すると一致する候補が表示されます。勝敗とメモは引き継ぎません。イベント選択肢は `2026/09/24：[店舗名] イベント名` の表記です。イベント詳細の使用デッキからレシピへ移動でき、対戦に紐付いた版があれば開いた状態で表示します。

### 公式PDFからデッキ登録

DECKSの「デッキを登録 / PDFから取り込む」を開き、公式サイトで発行したデッキ記入用紙PDFを選びます。MAINのモンスター・魔法・罠、EXTRA、SIDEをカード名と枚数ごとに読み取り、編集可能な欄に反映します。デッキ詳細の「新バージョンを作成」からPDFを選ぶと、そのデッキの新版として登録できます。PDFにはデッキ名欄がないため、ファイル名の末尾を初期値として使います。保存前に名前・枚数・合計を確認してください。PDFに記載された合計と読取枚数が異なる場合は警告を表示します。画像だけのPDFや異なる様式には対応しません。ファイルの解析は端末内で完結し、PDFそのものやカードゲームIDは保存・送信しません。レシピの表示と編集欄は `1《烙印融合》` 形式を使い、従来の `烙印融合 ×1` 形式も読み込めます。デッキ一覧ではカード名で全バージョンのMAIN・EXTRA・SIDEを検索でき、レシピ内のカードをタップして検索することもできます。カードは各区分でモンスター・魔法・罠・未分類ごとに色とアイコンで分け、種別内でカード名の昇順に表示します。PDFのMAINからは種別を読み取ります。手入力では `【魔法】` などの見出しに続けてカードを入力し、SIDEも種別を指定できます。旧レシピは種別を推測せず「未分類」と表示します。分類を追加する場合はそのレシピから新版を作成してください。

## 保存とバックアップ

対戦、ゲーム、デッキ、レシピ版、イベント、タグ、独自のレギュレーションと同期履歴はブラウザのIndexedDBに保存します。テーマ・クラウド接続設定はlocalStorageです。認証セッションはSupabase JSクライアントが保存します。設定の「保存データをすべて削除」で戦績などのIndexedDBレコードとテーマ設定を削除できます。同期の所有者情報は誤って別アカウントへ送信しないため保持します。端末の所有者情報まで消す場合は「端末データと同期履歴を消去」を使用してください。削除前には確認画面を表示します。固定のレギュレーション候補はアプリの一部として残ります。設定の「JSONをエクスポート」でバックアップし、「JSONから復元」で上書きまたはID単位でマージできます。Phase 1のJSON（schemaVersion 1）も読み込めます。ブラウザのデータ削除や別端末への移動に備えてJSONを保管してください。マージ時にIDが同じレコードは読み込んだ側を採用します。レシピ版は対戦からID参照されるため、新版追加で過去のレシピは変わりません。既存のバックアップや未設定のレギュレーションも引き続き読み込めます。デッキまたはイベントで使用中の独自レギュレーションは削除できません。

ANALYSISのCSVは現在選択中の期間・レギュレーション・店舗を対象に1 GAME 1行で出力します。MATCH情報は各行に繰り返し入り、同じ `matchId` でまとまります。対戦日を `playedAt` 列に出力します。UTF-8 BOM付きです。カード名等が表計算ソフトの式として実行されないよう、危険な先頭文字をエスケープしています。

## クラウド移行方針

UIは `AppService` → `IndexedDBRepository` で書き込み、同期処理は独立した `CloudController` → `SupabaseCloudRepository` を通じてクラウドへ反映します。端末の保存が先なので、オフラインでも対戦を記録できます。同期履歴はIndexedDB内に保持し、IDごとの変更・削除履歴を突き合わせます。全体統計やカード採用率を導入するときは、ユーザーの共有同意、デッキ名の正規化、集計用のサーバー側処理を追加します。

## レギュレーションの初期候補

[禁止・制限カードの改訂履歴](https://yugioh-wiki.net/?%B6%D8%BB%DF%A1%A6%C0%A9%B8%C2%A5%AB%A1%BC%A5%C9)と[リミットレギュレーションの改訂履歴](https://yugioh-wiki.net/?%A5%EA%A5%DF%A5%C3%A5%C8%A5%EC%A5%AE%A5%E5%A5%EC%A1%BC%A5%B7%A5%E7%A5%F3)の発効日をもとに、2000年4月1日から2026年10月1日までの各改訂を新しい順に選択肢にしています。表記は年下2桁＋月2桁、月初以外の改訂は日2桁も付けます（例：2607、000515）。各期間の終了日は次の改訂日の前日です。2026年10月1日以降は次の改訂日が確認できるまで継続中として表示します。前者の「1999」は月日が特定できないため日付付き候補には含めていません。候補はアプリに同梱され、利用者の独自期間のみ保存・バックアップ対象です。
