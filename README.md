# OCG RECORD

遊戯王OCGの戦績を、スマートフォンで記録する静的Webアプリです。GitHub Pagesでそのまま動きます。アカウントなしでも端末内で利用でき、用意されたSupabaseプロジェクトへ任意でログイン・同期できます。

## 機能（Phase 1〜4）

- 使用デッキ・相手デッキの候補付き入力。未登録の使用デッキは対戦保存時にレシピなしで登録し、レシピがあるデッキのみバージョンを選択
- デッキ登録、MAIN / EXTRA / SIDEのカード名と枚数、独立したレシピ版の追加・複製
- レシピ版ごとの変更履歴と、ひとつ前の版からのカード追加・削除・枚数変更の表示
- イベント登録とイベントごとの対戦一覧
- MATCH（最大3ゲーム）/ SINGLE記録。ゲーム別先後・勝敗、マッチ自動判定と手動修正、メモ・タグ、履歴の編集・削除
- HOMEの月間集計、ANALYSISの期間・デッキ・対面・ゲーム先後別の基本集計
- デッキ詳細に、そのデッキの全レシピ版を通したMATCH・GAME・SINGLEの勝率と対戦履歴を表示。履歴は並び替え・詳細確認が可能
- LIGHT / DARK / SYSTEM、全データのJSONエクスポート、上書き・マージ復元
- 任意のSupabaseプロジェクトとメールリンク／コード認証でログインし、端末間で戦績・デッキ・レシピ・大会・タグを同期
- ANALYSISの詳細表示：デッキ・対面ごとのMATCH / GAME / 先攻GAME / 後攻GAME、デッキバージョン比較、タグ別の勝敗
- 月別MATCH・SINGLE内訳グラフ（それぞれの対戦数と勝敗構成）、母数5 MATCH未満の注意表示
- 改訂日から用意したレギュレーションと独自期間の登録・削除・絞り込み、店舗別絞り込み、表示対象の対戦CSV出力と戦績CSV取り込み
- RECORDでライフ計算ツールの戦績CSVを取り込み、デッキ・対戦相手・イベントを対戦ごとに補完
- 遊戯王OCG公式サイト発行のデッキ記入用紙PDFから、カード名と枚数をMAIN / EXTRA / SIDEへ取り込む機能

黒曜石と金、紫を基調にした装飾的な画面です。SVGのカード絵と紋章、縁取り、階層化した面で各画面を演出します。LIGHT / DARK / SYSTEMでも入力と数値を読みやすくしています。

## 起動方法

ローカルではこのディレクトリで `python3 -m http.server 8000` を実行し、`http://localhost:8000` を開きます。`file://` で直接開くとES Modulesがブラウザの制限で動かない場合があります。

## GitHub Pages

このディレクトリの中身をリポジトリのルートへ置き、GitHubの **Settings → Pages → Build and deployment → Deploy from a branch** で対象ブランチの `/ (root)` を指定します。サブパスでも動くよう全アセットを相対パスで参照しています。ビルドは不要です。Supabaseの接続先は配布版に同梱せず、各端末で設定します。GitHub Pagesの公開操作とURL取得はリポジトリ所有者が行います。

## アプリ内ヘルプ

画面上部の「？」からヘルプページを開けます。記録・レシピ・イベント・分析・META・設定の各所にある「？」は、PCではマウスオーバー、スマートフォンではタップでその操作の説明を表示します。タップ後はもう一度アイコンを押すか、別の場所を押して閉じます。キーボードではフォーカス時に表示し、Escキーで閉じられます。

RECORDでは「＋ 対戦を追加」で対戦ごとのGAME欄を増やせます。不要な対戦欄は削除できます。対戦日・形式・使用デッキ・相手デッキ・イベント・タグ・メモは1回の入力を全件に適用し、各対戦のGAMEの先攻後攻・勝敗・結果の手動修正は個別に入力します。一括保存はIndexedDBの一つのトランザクションで処理します。入力途中の内容はページ再読込で消えるため、再読込前に保存してください。

HOMEの対戦履歴、EVENTSの店舗別対戦とイベント詳細のラウンド一覧は、新しい順（初期値）・古い順・勝ちを先に・負けを先に・相手デッキ名順で切り替えられます。両者敗北も「負けを先に」の対象です。デッキ一覧ではレシピが未登録のデッキを暗く表示し、開いてレシピを追加できます。

## iPhoneのホーム画面から使用

1. GitHub Pagesへこの版を公開した後、**Safari**で公開URLを開き、共有ボタンから「ホーム画面に追加」を選びます。追加した「OCG RECORD」アイコンから起動するとアプリ画面で開きます。アプリのURLとアイコン、オフライン用の画面・スクリプトはこの版に同梱しています。GitHub Pagesのリポジトリ配下でも動作します。
2. 初回はオンラインで起動してください。以後は一度読み込んだアプリを通信のない場所でも起動でき、対戦・デッキ・イベントを端末内へ記録できます。クラウド同期・認証メール・未読み込みのPDF解析用ファイルは通信が必要です。オンライン復帰時に同期を再試行します。
3. **Safariとホーム画面版は保存領域とログイン状態が別**です。Safariでメール内リンクを開いてもホーム画面版はログインしません。下記のSupabaseメールテンプレートにコードを追加し、ホーム画面版でコードを入力してください。Safariのみに保存した戦績は、Safariで同じアカウントへ同期してからホーム画面版へログインして取得するか、SafariでJSONバックアップを出力しホーム画面版で復元します。上書き復元の前にはバックアップしてください。
4. 更新版を公開すると、通信時に画面・スクリプトを再取得します。記録本体は端末のIndexedDBに残ります。iPhoneのストレージ削除やアプリの削除に備えて定期的にJSONを保存してください。

## クラウド同期の設定（Phase 3）

1. Supabaseプロジェクトを用意します。`ocg_records` テーブルが既に存在し、未ログインの読み取りが拒否されることを公開キーで確認済みです。初めて別のプロジェクトを利用する場合は、SQL Editorで [`sql/supabase.sql`](sql/supabase.sql) を実行して所有者ごとのRow Level Securityを設定します。
2. Authentication → ProvidersでEmailログインを有効にします。Authentication → URL ConfigurationのSite URL / Redirect URLsに、公開したGitHub PagesのURL（リポジトリのサブパスを含む `https://<user>.github.io/<repo>/`）を設定します。メールの送信設定や利用上限はSupabase側の設定に従います。
3. アプリの設定画面でプロジェクトURLと **publishable key** を入力して「接続先を保存」を押します。初期値は空欄です。すでに端末に保存した接続先は更新後も引き続き表示・利用されます。**service_role / secret keyは絶対に入力しないでください。**
4. **ホーム画面版でのログインにはSupabase側のメール設定が必要です。** Supabase Dashboard の **Authentication → Email Templates → Magic Link** を開き、メール本文に `<p>ログインコード: {{ .Token }}</p>` を追加して保存します。既存の `{{ .ConfirmationURL }}` のリンクは残して構いません。この設定をするまではメールにコードが載らないため、ホーム画面版のコード認証は使えません。
5. ホーム画面版では設定の「ログインメールを送信」でメールを送り、同じ画面の「ログインコード」に届いたコードを入力します。Safariで開いた場合は従来のリンク認証も使えます。最初の同期で既存の端末データとクラウドのデータをIDごとに突き合わせます。二台目以降も同じメールアカウントでログインしてください。

ログイン後は保存・編集・削除時、オンライン復帰時、タブへ戻ったときに同期します。「今すぐ同期」でも実行できます。通信が失敗した場合は端末内データが残り、次回同期を試せます。 iPhoneでページが休止されIndexedDB接続が閉じた場合は、次の読み書き時に再接続して一度だけ処理を再試行します。削除も同期対象です。競合は各レコードの`updatedAt`を比較して新しい方を採用し、同時刻ならクラウド側を採用します。同期の途中で端末データが変更された場合は端末内の変更を保護し、次回の同期で再試行します。**端末の時計のずれや、同時刻の同一レコード編集では片方が上書きされ得ます。** 大切な変更の前後はJSONを保管してください。

初回同期後の端末データはログインしたアカウントに紐付きます。ログアウトしても端末内データは残ります。別アカウントを使う場合はJSONを保管し、「端末データと同期履歴を消去」で端末を空にしてからログインします。この操作でクラウド上のデータは消えません。「保存データをすべて削除」は、ログイン中なら次回同期時にクラウド側のデータも削除します。**クラウドへの削除反映を確認してからログアウトしてください。**

起動時に同期用ライブラリをjsDelivrから取得します。取得できなくても戦績の端末内保存は動作します。認証メールの配送設定とGitHub PagesのリダイレクトURL登録はプロジェクト側で別途必要です。Supabase標準メール配送はチームに登録された宛先以外を拒否するため、一般ユーザーへ公開する場合は独自SMTPが必要です。

## Phase 4: みんなの環境

**現在META機能は一時停止中です。** ナビゲーションから非表示とし、閲覧・新規共有・共有更新を停止しています。クラウド同期は継続します。既存の共有データは保持され、ログイン中の設定画面から共有を取り消せます。再有効化時のため実装とSQLは残しています。

1. 既存の `sql/supabase.sql` を適用済みのSupabaseプロジェクトで、SQL Editorから [`sql/community.sql`](sql/community.sql) を実行します。Phase 4のテーブルと集計関数が追加されます。既存の対戦データは変更しません。
2. METAを再有効化した後、ログインして下部の **META** を開きます。未ログイン時はMETAを表示しません。集計はログイン済みユーザーだけが閲覧できます。
3. 自分の記録を使った共有は初期状態で無効です。「内容を確認して共有」を押したときだけ、その時点の内容を送信します。送信されるのは最新1000件以内のMATCHについて月・使用デッキ・相手デッキ・勝敗、各デッキの最新版レシピのカード名とMAIN/EXTRA/SIDE区分です。メール・氏名・店舗・イベント・対戦日・メモ・各カードの枚数は送信しません。送った採用カード一覧は本人だけが参照でき、他者へは5人以上の集計行のみ返します。編集後は「共有内容を更新」を押してください。取り消し操作、またはログイン中の「保存データをすべて削除」で共有内容を削除します。取り消しにはログインとネット接続が必要です。ログアウト中に端末データだけを消去すると公開スナップショットは残るため、事前にログインして取り消してください。
4. SQL側で1分類につき5人以上の共有者がいる行だけ表示します。共有者が少ない間は空欄です。自己申告された対戦記録を集約した参考値であり、OCG全体の統計ではありません。カード採用人数は各人の同名デッキの最新版レシピを対象とし、同名デッキの重複はその人について1回として数えます。

Phase 4のSQLが未適用の場合、METAには読み込みエラーが出ます。クラウドの個人用同期と端末内の記録は従来どおり利用できます。実際のSupabaseプロジェクトへのSQL適用と複数アカウントでの動作確認は、配布後に行ってください。

## データモデル

| エンティティ | 主なフィールド | 関係 |
| --- | --- | --- |
| User（将来） | id | 初期版の全レコードの `userId` は `null` |
| Event | id, userId, name, date, venue, regulationId, deckId, rank, participants, notes | Match 1対多 |
| Match | id, userId, eventId, deckId, deckVersionId, opponentDeckName, opponentDeckId, format, playedAt, result, resultSource, notes, tags | Game 1対多。`opponentDeckId` は将来の正規化用 |
| Game | id, userId, matchId, number, turn, result | 先後・勝敗は各ゲームに属する |
| Deck | id, userId, name, regulationId | DeckVersion 1対多 |
| DeckVersion | id, userId, deckId, label, cards | 保存後は内容を変更せず、新版を作る |
| DeckCard | `DeckVersion.cards.main/extra/side` 内の `{id, cardId, name, count, type}` | `cardId` は将来カード辞書を導入した際に使用 |
| Tag | id, userId, name | Match の `tags` に文字列配列も保持 |
| Period | id, userId, label, startDate, endDate | 独自のレギュレーション。固定の初期候補はアプリ内で生成し保存しない |

各主要レコードにはUUIDと `createdAt`, `updatedAt` を保存します。Eventの日付は `date`、Matchの対戦日は `playedAt` です。以前のバックアップに時刻のフィールドが含まれていても読み込みは継続できます。MATCHとGAMEの集計母数は別々です。先後別勝率は各ゲーム単位で算出し、MATCHに先攻・後攻を割り当てません。引き分けは勝率の分母に含め、分子には含めません。両敗は敗北に含めます。相手デッキ名は自由入力です。使用デッキ名も候補付き自由入力で、未登録名は保存時にレシピなしのDeckとして自動登録します。版のあるデッキを選ぶと版の選択が有効になります。後から版を追加しても過去の「版なし」記録は変わらず、その記録の編集時にも維持できます。月別グラフはMATCHのみを表示します。

## 画面と主要フロー

HOME（概要・履歴）→ DECKS（デッキ・レシピ版とレギュレーションを登録）→ EVENTS（任意でレギュレーション・大会を登録）→ RECORD（デッキ版と相手、ゲーム別結果を記録）→ HOME / ANALYSIS（振り返り）。記録は履歴を開いて編集・削除できます。設定にはHOME右上から移動します。イベント詳細から名称・日付・店舗・レギュレーション・使用デッキ・順位・人数・メモを編集できます。既存の対戦との紐付けは維持されます。イベントの店舗は過去の登録から候補を選ぶか新しい名前を入力できます。EVENTSの店舗選択で、その店舗のイベントと対戦履歴を確認できます。ANALYSISでは集計期間・レギュレーション・店舗・イベント名を組み合わせて絞り込めます。イベント名はひらがな・カタカナを区別せず部分一致で候補が表示され、イベント未設定の対戦は「フリー対戦」で検索できます。対戦履歴にも「フリー対戦」と表示します。対戦のレギュレーションはイベント設定、使用デッキ設定、対戦日の順に判定します。RECORDは直近の入力から対戦日・形式・使用デッキと版・イベント・ゲームごとの先後を引き継ぎます。使用デッキと相手デッキは同じ形式の入力・候補欄です。相手デッキは毎回選び直します。過去の相手デッキは昇順で表示され、文字を入力すると一致する候補が表示されます。勝敗とメモは引き継ぎません。イベント選択肢は `2026/09/24：[店舗名] イベント名` の表記です。イベント詳細の使用デッキからレシピへ移動でき、対戦に紐付いた版があれば開いた状態で表示します。

### 公式PDFからデッキ登録

DECKSの「デッキを登録 / PDFから取り込む」を開き、公式サイトで発行したデッキ記入用紙PDFを選びます。MAINのモンスター・魔法・罠、EXTRA、SIDEをカード名と枚数ごとに読み取り、編集可能な欄に反映します。デッキ詳細の「新バージョンを作成」からPDFを選ぶと、そのデッキの新版として登録できます。PDFにはデッキ名欄がないため、ファイル名の末尾を初期値として使います。保存前に名前・枚数・合計を確認してください。PDFに記載された合計と読取枚数が異なる場合は警告を表示します。画像だけのPDFや異なる様式には対応しません。ファイルの解析は端末内で完結し、PDFそのものやカードゲームIDは保存・送信しません。レシピの表示と編集欄は `1《烙印融合》` 形式を使い、従来の `烙印融合 ×1` 形式も読み込めます。デッキ一覧ではカード名で全バージョンのMAIN・EXTRA・SIDEを検索でき、レシピ内のカードをタップして検索することもできます。カードはMAIN・EXTRA・SIDEそれぞれで入力した順番に表示します。過去のレシピとPDFから読み取った種別情報はデータ内に残りますが、表示や編集時の分類には使いません。採用カードの検索欄はひらがな・カタカナを区別せず部分一致で候補を出し、一致したデッキ数と全レシピ版の採用箇所数を表示します。

デッキ詳細では各レシピ版を削除できます。対戦で使用中の版を削除した場合、該当する対戦は残したまま版の指定だけを外します。最後の版を削除してもデッキ本体は残ります。削除前に影響する対戦数を確認できます。デッキ詳細のレシピ履歴は保存日時の新しい順に表示します。各版の見出しに前版との差分を表示し、開くとMAIN / EXTRA / SIDEごとのカードの追加・削除、枚数の増減を確認できます。増加は青、減少は赤で、変動枚数にかかわらず一律の濃さでカード行と枚数表示を色分けし、枚数と符号も併記します。種別情報だけの違いは差分に含めません。MAINからSIDEなど区分を移したカードは、元の区分で削除・移動先で追加として表示します。最初の版は「初版」と表示します。差分は保存済みの版を表示時に比較して計算するため、既存レシピのデータや過去の対戦への紐付けは変更しません。

## 保存とバックアップ

対戦、ゲーム、デッキ、レシピ版、イベント、タグ、独自のレギュレーションと同期履歴はブラウザのIndexedDBに保存します。テーマ・クラウド接続設定はlocalStorageです。認証セッションはSupabase JSクライアントが保存します。設定の「保存データをすべて削除」で戦績などのIndexedDBレコードとテーマ設定を削除できます。同期の所有者情報は誤って別アカウントへ送信しないため保持します。端末の所有者情報まで消す場合は「端末データと同期履歴を消去」を使用してください。削除前には確認画面を表示します。固定のレギュレーション候補はアプリの一部として残ります。設定の「JSONをエクスポート」でバックアップし、「JSONから復元」で上書きまたはID単位でマージできます。Phase 1のJSON（schemaVersion 1）も読み込めます。ブラウザのデータ削除や別端末への移動に備えてJSONを保管してください。マージ時にIDが同じレコードは読み込んだ側を採用します。レシピ版は対戦からID参照されるため、新版追加で過去のレシピは変わりません。既存のバックアップや未設定のレギュレーションも引き続き読み込めます。デッキまたはイベントで使用中の独自レギュレーションは削除できません。

ANALYSISのCSVは現在選択中の期間・レギュレーション・店舗を対象に1 GAME 1行で出力します。MATCH情報は各行に繰り返し入り、同じ `matchId` でまとまります。対戦日を `playedAt` 列に出力します。UTF-8 BOM付きです。カード名等が表計算ソフトの式として実行されないよう、危険な先頭文字をエスケープしています。

設定の「戦績CSVを取り込む」から、このアプリのANALYSISで出力したCSVを選べます。取り込み前に新規・重複の対戦件数を確認できます。同じ `matchId` の対戦はスキップし、既存の対戦は上書きしません。デッキ名で既存デッキを探し、なければレシピなしのデッキを追加します。レシピ版は同じデッキ内に同じ版名が一つだけある場合に紐付けます。イベントは名前・店舗・対戦日が一致すれば既存を使用し、なければ作成します。CSVにはレシピ本体・イベントの順位などは含まれません。これらを含む完全な移行にはJSONバックアップを使ってください。取り込み中に端末内の記録が変更された場合は保存せず再選択を求めます。

### ライフ計算ツールとの戦績連携（出力機能追加時のCSV仕様）

RECORDの「ライフ計算ツールの戦績CSVを取り込む」から、ライフ計算ツール専用のCSVを選びます。計算ツール側には現在このCSV出力機能がありません。将来、計算ツール側に出力を実装するときは、下記のヘッダーで**終了済みGAMEを1行ずつ**出力してください。UTF-8（BOMの有無は問いません）、カンマ区切り、通常のCSV引用符に対応します。MATCHは同じ `recordId` の行で束ね、SINGLEは1行1対戦です。

| 列 | 値 | 備考 |
| --- | --- | --- |
| `recordId` | UUID | MATCHまたはSINGLEごとに生成し、再出力しても同じIDを使う。重複取込防止に必須 |
| `playedAt` | `YYYY-MM-DD` | 対戦日。計算ツール側で記録・出力する |
| `format` | `MATCH` / `SINGLE` | 形式 |
| `gameNumber` | `1`〜`3` | MATCH内で1から連番。SINGLEは`1` |
| `firstPlayer` | `p1` / `p2` | そのGAMEの先攻側 |
| `winner` | `p1` / `p2` / `DRAW` | そのGAMEの勝者。未確定GAMEは出力しない |

例：

```csv
recordId,playedAt,format,gameNumber,firstPlayer,winner
19d33135-7660-4c5a-b163-cd64073ffbbc,2026-09-24,MATCH,1,p1,p2
19d33135-7660-4c5a-b163-cd64073ffbbc,2026-09-24,MATCH,2,p2,p1
```

**ライフ残量・変動履歴・ターンごとの操作はCSVに出力しません。** 現行の計算ツールのログにはGAMEごとの勝者・先攻・MATCH番号がありますが、固定の対戦IDと対戦日がないため、出力機能の実装時に追加が必要です。CSV取り込み画面では各対戦について自分がP1/P2のどちらか、使用デッキ、相手デッキ、既存イベントまたは新しいイベントの内容・会場を指定します。レシピ版とメモは任意です。自分側に換算したGAME結果から対戦結果を判定し、ET・ED・両敗などは手動で修正できます。イベントを新規作成する場合の開催日はCSVの対戦日です。既存の `recordId` はスキップして上書きしません。まとめて100対戦まで取り込めます。保存中に端末の記録が変わった場合は全件保存せず再選択を求めます。

## クラウド移行方針

UIは `AppService` → `IndexedDBRepository` で書き込み、同期処理は独立した `CloudController` → `SupabaseCloudRepository` を通じてクラウドへ反映します。端末の保存が先なので、オフラインでも対戦を記録できます。同期履歴はIndexedDB内に保持し、IDごとの変更・削除履歴を突き合わせます。Phase 4の集計は明示的な共有同意の後に別のスナップショットを作り、サーバー側の集計関数が5人以上の分類を返します。デッキ名は入力された表記で分類されるため、表記違いは別のテーマとして集計されます。

## レギュレーションの初期候補

[禁止・制限カードの改訂履歴](https://yugioh-wiki.net/?%B6%D8%BB%DF%A1%A6%C0%A9%B8%C2%A5%AB%A1%BC%A5%C9)と[リミットレギュレーションの改訂履歴](https://yugioh-wiki.net/?%A5%EA%A5%DF%A5%C3%A5%C8%A5%EC%A5%AE%A5%E5%A5%EC%A1%BC%A5%B7%A5%E7%A5%F3)の発効日をもとに、2000年4月1日から2026年10月1日までの各改訂を新しい順に選択肢にしています。表記は年下2桁＋月2桁、月初以外の改訂は日2桁も付けます（例：2607、000515）。各期間の終了日は次の改訂日の前日です。2026年10月1日以降は次の改訂日が確認できるまで継続中として表示します。前者の「1999」は月日が特定できないため日付付き候補には含めていません。候補はアプリに同梱され、利用者の独自期間のみ保存・バックアップ対象です。
